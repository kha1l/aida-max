# Базовый уровень безопасности

Этот репозиторий участвует в формировании базового уровня безопасности в рамках родительской задачи Trelio 543.

## Сообщение об уязвимости

Сообщения об уязвимостях принимаются по адресу
[support@dev-vkus.ru](mailto:support@dev-vkus.ru).

Укажите затронутый компонент, наблюдаемый эффект и минимальные безопасные шаги
воспроизведения. Не отправляйте токены, пароли, приватные ключи, recovery
codes, kubeconfig, значения Secret, персональные данные или полный production
payload.

Целевые сроки:

- подтверждение получения — 1 рабочий день;
- первичная классификация — 3 рабочих дня;
- первый содержательный статус — 5 рабочих дней;
- подтверждённые Critical/High — немедленная эскалация.

## Область, архитектура и доверительные границы

`aida_max` — MAX-бот Aida. Недоверенные входы: события MAX, deeplink и
пользовательские команды. Привязка аккаунта выполняется через Aida-связанный
endpoint `dodovkus`; внутренние интеграции — PostgreSQL, Redis, RabbitMQ и
Dagster GraphQL. Consumer использует `chat_id` из внутреннего RabbitMQ payload
без повторной проверки связки с аккаунтом.

Пользовательские MAX-входы проверяются по deeplink, пользовательскому
контексту и разрешённой операции. Для доставки через RabbitMQ доверительными
предпосылками являются ограниченный круг Aida-producers, ACL брокера и
проверка связки до формирования payload. Компрометация producer или подмена
`chat_id` остаётся риском до добавления повторной проверки в consumer.
Административный доступ к runtime выполняется только по пути AWG → bastion с
TOTP → ресурс с персональным ключом. VLESS в административный контур не
входит.

## Данные и секреты

Компонент обрабатывает MAX `user_id` и `chat_id`, связку с Dodo-аккаунтом,
настройки, подписки, идентификаторы точек и содержимое отчётов. Источники —
MAX, `dodovkus` и внутренние сервисы Aida; получатели — связанные
пользователи и чаты MAX. Данные используются для авторизации, настроек и
доставки отчётов.

Секретами являются bot token, реквизиты PostgreSQL, Redis/RabbitMQ и Dagster
auth. Значения хранятся только в Kubernetes Secret или защищённом окружении
и не включаются в Git, логи или этот документ. Доступ имеют назначенные
владельцы; ротация обязательна после утечки, отзыва доступа, потери устройства
или смены интеграции. Сроки хранения и удаление задаются централизованным
реестром данных Aida; данные не хранятся дольше цели обработки.

## Модель угроз и OWASP Top 10

Для event-driven бота без browser DOM классические XSS и cookie-based CSRF
неприменимы внутри этого компонента. SSRF, IDOR, небезопасная десериализация,
инъекции и остальные категории сохраняют применимость:

| OWASP Top 10:2025 | Применимость и основные меры |
| --- | --- |
| A01 Broken Access Control | Серверная проверка deeplink, пользовательского контекста и связки аккаунта; отказ фиксируется как `access_denied` |
| A02 Security Misconfiguration | Закрытый административный контур, Kubernetes Secret, минимальные настройки контейнера и сканирование конфигурации Trivy |
| A03 Software Supply Chain Failures | Dependabot, Trivy, SBOM, закреплённые Actions и проверка точного container image |
| A04 Cryptographic Failures | TLS, защищённое хранение ключей и запрет чувствительных данных в логах |
| A05 Injection | Валидация событий и deeplink, параметризованный ORM, безопасное формирование сообщений и Semgrep |
| A06 Insecure Design | Явные trust boundaries, одноразовый bind-flow, минимальные права и отдельное решение по DAST |
| A07 Authentication Failures | Делегированная Dodo-аутентификация, проверка MAX-контекста и MFA/TOTP для административного доступа |
| A08 Software or Data Integrity Failures | Целостность RabbitMQ опирается на ограниченных producers и ACL брокера; consumer пока не перепроверяет связку `chat_id`; дополнительно применяются подписанный bind-flow, SBOM и контроль commit/image |
| A09 Security Logging and Alerting Failures | Отдельный поток `security_audit`, синтетические идентификаторы, Loki и Alertmanager |
| A10 Mishandling of Exceptional Conditions | Fail-closed на границе доступа, ограниченные timeout/retry, безопасные ошибки и runbook |

## Безопасная эксплуатация и инциденты

- изменения выполняются через Pull Request с независимым ручным review;
- после нового commit изменившийся diff проверяется повторно;
- прямой и force-push в `main` запрещены; merge выполняет тимлид;
- при компрометации ограничить функцию, отозвать или ротировать фактор,
  сохранить минимальное evidence без секретов и уведомить владельцев;
- после восстановления проверить логи и алерты, зафиксировать причину и
  корректирующие действия.

## Автоматические проверки

| Проверка | Назначение | Блокирующее условие |
| --- | --- | --- |
| `Security / AITriage` | Детерминированные встроенные проверки AITriage | Профиль политики `standard`; любая активная находка уровня Critical или High |
| `Security / Semgrep` | SAST-анализ исходного кода с зафиксированными community rules | Находки уровня `ERROR` в категории `security`, а также ошибки сканера или правил |
| `Security / Gitleaks` | Поиск секретов в диапазоне pull request или во всей истории Git | Любая находка; обнаруженные значения полностью скрываются в отчёте |
| `Security / Trivy` | Уязвимости зависимостей, ошибки конфигурации IaC/Docker/GitHub Actions и CycloneDX SBOM | Находки уровня High или Critical |
| `Security / Evidence` | Сводные статусы, версии инструментов, метаданные запуска и SHA-256 артефактов | Отсутствующий или неуспешный результат любого сканера |

Bandit намеренно исключён. Сканирование секретов в Trivy также отключено, поскольку за эту проверку отвечает Gitleaks.

AITriage и Trivy формируют доказательные артефакты CycloneDX SBOM. Workflow записывает репозиторий, commit и версию компонента в SBOM от AITriage, а также сохраняет метаданные базы уязвимостей Trivy, использованной плановой CVE-проверкой.

Workflow запускается для pull request, push в основную ветку, ручного запуска и по еженедельному расписанию со сдвигом времени. Он использует GitHub token только для чтения, не сохраняет учётные данные checkout, фиксирует сторонние Actions по commit SHA, а версии сканеров и контейнерные образы — по digest.

Отчёты сохраняются как артефакты GitHub Actions на 90 дней. Ошибка сканера остаётся ошибкой и после загрузки артефактов; недоступный инструмент никогда не считается успешной проверкой.

## Обновление зависимостей

Dependabot настроен для используемых в репозитории экосистем пакетов, Dockerfile при их наличии и GitHub Actions. Обычные minor- и patch-обновления группируются. Обновления безопасности остаются отдельными от обычных групп обновления версий.

После слияния этой ветки в настройках репозитория или организации также необходимо включить Dependabot alerts и автоматические обновления безопасности.

## Решение по DAST

DAST неприменим к текущему сервису: бот обрабатывает события платформы и сообщения RabbitMQ и не имеет публичного входящего HTTP endpoint. Внешний endpoint привязки учётной записи принадлежит `dodovkus` и входит в его staging-область DAST.

## Аудит security-событий

Security-события отправляются как отдельный JSON-поток `security_audit`.
Журналируются только границы безопасности:

- результат привязки MAX-аккаунта по deeplink;
- факт принятия одноразового deeplink credential без его значения;
- успешная проверка пользовательского контекста при запуске бота;
- отказ в запуске без пользовательского контекста.

Обычные сообщения, callback-навигация и внутренние запросы пользовательского
контекста audit-событий не создают. Для одной операции используется общий
`request_id`/`trace_id`; токен, deeplink, ФИО, username, телефон и email в
событие не передаются.

Административных операций, изменения ролей, прав, конфигурации или секретов в
этом приложении нет, поэтому фиктивные события для них не создаются.

## Сборка контейнера и проверка образа

Обязательный контейнерный workflow собирает приложение, запускает тесты security logging внутри точного образа, создаёт CycloneDX SBOM образа и полный отчёт по HIGH/CRITICAL, а также блокирует исправимые находки HIGH/CRITICAL. После успешного завершения основного scanner workflow для того же commit релиз публикует в GHCR только этот уже проверенный образ с commit SHA и очищенным release tag; тег `latest` не публикуется.

## Исключения

Это изменение не добавляет широких исключений по правилам или путям. Если присутствует `.gitleaksignore`, он содержит только точные fingerprints исторических находок; такие записи не отменяют необходимость ротации значения, которое когда-либо являлось настоящим credential. Каждое исключение должно содержать:

- точное правило или fingerprint;
- причину, по которой находка является false positive или принятым риском;
- ответственного;
- дату окончания или пересмотра;
- компенсирующую меру.
